# DocuSpec: Полный пайплайн от рабочей документации до сметы

## Обзор системы

Система автоматизирует цепочку: **PDF рабочей документации → распознавание → извлечение материалов → составление сметы с расценками ФСНБ-2022**.

Стек: React 19 + TypeScript + Vite (фронтенд), Supabase/PostgreSQL (БД), OpenRouter → Claude/GPT (LLM), Ant Design 5 (UI).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         ПОЛНЫЙ ПАЙПЛАЙН DOCUSPEC                            │
│                                                                             │
│  ┌──────────┐    ┌──────────────┐    ┌───────────────┐    ┌──────────────┐ │
│  │ ЭТАП 0   │    │   ЭТАП 1     │    │   ЭТАП 2      │    │   ЭТАП 3     │ │
│  │ Внешний  │───►│ Парсинг и    │───►│ Извлечение    │───►│ Составление  │ │
│  │ OCR/PDF  │    │ загрузка     │    │ материалов    │    │ сметы        │ │
│  │ → MD     │    │ MD → БД      │    │ (3+1 фазы)   │    │ (3 агента)   │ │
│  └──────────┘    └──────────────┘    └───────────────┘    └──────────────┘ │
│  (не DocuSpec)    (существует)        (существует)         (НОВОЕ, MVP)    │
└─────────────────────────────────────────────────────────────────────────────┘
```

## ЭТАП 0: Распознавание документов (внешний, входные данные)

**Вне DocuSpec.** PDF рабочей документации обрабатывается внешним OCR-сервисом, который выдаёт два файла:

### Выходные файлы

**1. `*_document.md`** — структурированный Markdown:
```markdown
# 133/23-ГК-АР6
Сгенерировано: 2024-12-15
**Штамп:** 133/23-ГК-АР6 | РД | Жилой комплекс, Мосфильмовская 31А | ОЛИМПРОЕКТ

## СТРАНИЦА 1
### BLOCK [TEXT]: A1B2C3
#### Спецификация элементов ограждений
| Поз. | Обозначение | Наименование | Кол.шт | Примечание |
|------|-------------|-------------|--------|-----------|
| — | — | **ОГ-13, L=4 700** | **1** | Крепление на ступень |
| 1 | ГОСТ 9941-81 | Стальная прутья 30x15x2 мм | **1** | |
| 2 | ГОСТ 103-2006 | Полоса стальная С245: 8x20 мм, L=1 185 | **13** | |
...

### BLOCK [IMAGE]: D4E5F6
**[ИЗОБРАЖЕНИЕ]** | Тип: Разрез
**Текст на чертеже:** Облицовка плитами гранита на клею -20мм |
ЦПР стяжка М150 арм. мет. сеткой -40мм | Обмазочная битумная гидроизоляция -2 слоя
```

**2. `*_result.json`** — компаньон с URL изображений блоков из PDF (для визуального анализа чертежей).

### Формат MD-файла
- `## СТРАНИЦА N` — разделитель страниц
- `### BLOCK [TEXT|IMAGE]: UID` — блок (текстовый или изображение)
- `#### Заголовок` — название секции/раздела
- Таблицы — стандартный Markdown с `|`
- IMAGE блоки: `Тип: Разрез|Сечение|Узел|Легенда|План` + `Текст на чертеже:` (OCR-текст с чертежа)

## ЭТАП 1: Парсинг и загрузка (существует)

**Модуль**: `src/lib/parser.ts` + `src/hooks/useDocument.ts`

### Что происходит

1. Пользователь загружает MD-файл (+ опционально JSON-компаньон) через Drag-and-Drop на HomePage
2. Выбирает проект и раздел документации (АР, КЖ, КМ, ОВ, ВК, ЭОМ...)
3. Парсер разбирает MD в структуру:

```
ParsedDocument
  ├─ title: "133/23-ГК-АР6"
  ├─ docCode: "133/23-ГК-АР6"
  ├─ stampText: "РД | Жилой комплекс..."
  └─ pages[]
       ├─ pageNo: 1
       └─ blocks[]
            ├─ uid: "A1B2C3"
            ├─ type: "TEXT"
            ├─ content: "#### Спецификация...\n| Поз. | ..."
            ├─ tables[]
            │    ├─ headers: ["Поз.", "Обозначение", "Наименование", "Кол.шт"]
            │    ├─ rows: [["—", "—", "ОГ-13, L=4 700", "1"], ...]
            │    └─ sectionContext: "Спецификация элементов ограждений"
            └─ sectionTitle: "Спецификация элементов ограждений"
```

4. Сохранение в БД (Supabase):
   - `documents` — головная запись (filename, raw_md, doc_code, status, project_id, section_id)
   - `doc_pages` — страницы (page_no, sheet_label)
   - `doc_blocks` — блоки (block_uid, block_type, content, has_table, section_title, image_url)

### Результат этапа
Документ в БД со status='uploaded', разбитый на страницы и блоки. Готов к извлечению.

## ЭТАП 2: Извлечение материалов (существует)

**Модуль**: `src/hooks/useExtraction.ts` + `src/lib/extraction.ts` + `src/lib/tableClassifier.ts`

Пользователь нажимает "Извлечь материалы" на DocumentPage. Запускается многофазный пайплайн:

### Фаза 0: Глоссарий

**Что делает**: Собирает все коды и сокращения из документа (ОГ-13, RAL 9001, П1, Л-7...)

**Как работает**:
1. Все TEXT-блоки > 50 символов разбиваются на chunks (~25 блоков)
2. Каждый chunk отправляется в LLM с промптом `glossary_extraction`
3. LLM возвращает массив: `[{code: "ОГ-13", item_type: "assembly", description: "Ограждение 13"}, ...]`
4. Дедупликация по code → сохранение в `doc_glossary`

**Результат**: `glossaryMap` — словарь сокращений, используется далее для контекста.

### Классификация блоков

**Что делает**: Каждый блок с таблицей классифицируется по типу (`tableClassifier.ts`).

**13 категорий таблиц**:

| Категория | Как определяется | Обработка |
|-----------|-----------------|-----------|
| `vedomost_materialov` | Секция "ведомость материалов" | **Фаза 1** — ведомости |
| `material_qty` | Колонки: наименование + количество + ед.изм | **Фаза 1** — ведомости |
| `assembly_spec` | Секция "спецификация элементов ограждений" | **Фаза 2b** — сборки |
| `vedomost_izdelij` | Секция "ведомость изделий/ограждений" | **Фаза 2c** — изделия |
| `spec_elements` | Колонки: поз + обозначение + наименование + кол-во | **Фаза 2** — спецификации |
| `element_spec` | Колонки: марка + описание + кол-во | **Фаза 2** — спецификации |
| `floor_spec` | "тип пола" или "данные элементов" | **Фаза 2** — спецификации |
| `roof_spec` | "тип покрытия" + "данные элементов" | **Фаза 2** — спецификации |
| `change_log` | "изм" + "подп"/"дата" | Пропускается |
| `room_schedule` | "№ пом" + "площадь" | Пропускается |
| `reference_docs` | "обозначение" + "наименование" + "примечание" (без кол-во) | Пропускается |
| `drawing_list` | "№ листа" + "наименование" (без кол-во) | Пропускается |
| `unknown` | Не совпадает ни с одним | **Фаза 2** — через LLM |

**Результат распределения**:
- `vedomostBlocks` → Фаза 1
- `specBlocks` → Фаза 2
- `assemblyBlocks` → Фаза 2b
- `productListBlocks` → Фаза 2c
- `imageBlocks` → Фаза 3

### Фаза 1: Ведомости материалов

**Что делает**: Извлекает материалы из ведомостей — таблиц с прямыми перечнями материалов и их количествами.

**Алгоритм**:
1. Для каждого vedomostBlock → rule-based извлечение (`ruleBasedExtract`):
   - Ищет колонки: Наименование, Количество, Ед.изм., ГОСТ, Марка, Примечание
   - Парсит русские числа ("202,6" → 202.6, "1 692,9" → 1692.9)
   - Если unit="мм" → это толщина, перемещается в description
2. Если rule-based вернул 0 результатов → блок отправляется в LLM
3. Результат: массив `MaterialFactItem` для каждого блока

**Пример входа** (таблица в блоке):
```
| № | Обозначение | Наименование | Объем, м³ | Примечание |
|---|-------------|-------------|----------|-----------|
| 4 | ГОСТ 530-2012 | Кирпич полнотелый КР-р-по 250x120x65 | 7,13 | Армируется ВР сеткой |
```

**Пример выхода** (MaterialFactItem):
```json
{
  "raw_name": "Кирпич полнотелый КР-р-по 250x120x65/1НФ/150/2,0/50",
  "gost": "ГОСТ 530-2012",
  "quantity": 7.13,
  "unit": "м3",
  "note": "Армируется ВР сеткой",
  "source_section": "vedomost_materialov",
  "block_type_display": "Таблица",
  "confidence": 0.95
}
```

### Фаза 2: Спецификации

**Что делает**: Извлекает материалы из спецификаций — таблиц с элементами конструкций.

**Алгоритм**:
1. Rule-based для известных типов таблиц (spec_elements, element_spec)
2. Для "сложных" и unknown таблиц → LLM с промптом `universal_extraction`
3. Merge: rule-based результаты имеют приоритет, LLM дополняет

**Особенности**:
- Двухколоночные таблицы: "Наименование элементов" (→ construction) + "Наименование материала" (→ raw_name)
- RAL-коды извлекаются в `extra_params`
- Generic names ("по проекту") заменяются на текст из description

### Фаза 2b: Спецификации сборок (assembly_spec)

**Что делает**: Обрабатывает спецификации типа "состав ограждения ОГ-13".

**Особенность**: создаёт **и** material_facts (компоненты), **и** product_facts (сборки).

**Пример**:
```
ОГ-13, L=4700          →  product_fact: assembly_mark="ОГ-13", quantity=1
├─ Стальная труба 30x15 →  material_fact: raw_name="Стальная труба", construction="ОГ-13", qty=1
├─ Полоса стальная      →  material_fact: construction="ОГ-13", qty=13
└─ Хим. анкер 8x105     →  material_fact: construction="ОГ-13", qty=28
```

### Фаза 2c: Ведомости изделий (vedomost_izdelij)

**Что делает**: Извлекает количества готовых изделий (сколько штук ОГ-13 на объекте).

**Результат**: product_facts с qty_scope='total'

### Движок умножения (assembly_spec × vedomost_izdelij)

**Что делает**: Если есть и состав сборки (Фаза 2b), и количество сборок (Фаза 2c) — рассчитывает итоговый расход материалов.

**Пример**:
- Материал "Полоса стальная" в ОГ-13: qty=13, qty_scope='per_unit'
- Изделие ОГ-13 в ведомости: quantity=5
- **Результат**: 13 × 5 = 65 шт → source_section='assembly_total', calc_note="ОГ-13 × 5 шт: 13 × 5 = 65"

### Фаза 3: Пироги конструкций (IMAGE блоки)

**Что делает**: Извлекает слои конструкций из чертежей разрезов/сечений/узлов.

**Алгоритм**:
1. Берёт "Текст на чертеже:" из IMAGE-блока + опциональное изображение (image_url)
2. Отправляет в LLM с промптом `layer_cake`
3. LLM выделяет слои: название материала + толщина + порядок (от внешнего к внутреннему)

**Пример** (из чертежа "Сечение Л7-Л7"):
```
Слой 1: Облицовка плитами гранита на клею — 20мм
Слой 2: ЦПР стяжка М150 арм. мет. сеткой — 40мм
Слой 3: Обмазочная битумная гидроизоляция — 2 слоя
Слой 4: ЦПР стяжка М150 — 20мм
Слой 5: Монолитные Ж/Б ступени
```

Каждый слой → material_fact с source_section='pirog', construction="Сечение Л7-Л7".

### Пост-обработка (enrichMaterialFacts)

Для каждого material_fact проставляется:
- **kind**: 'material' или 'equipment' (по паттернам: "насос", "вентилятор", "кВт" → equipment)
- **qty_scope**: 'per_unit' (на 1 изделие), 'total' (итого), 'unknown'
- **needs_review**: true если confidence < 0.5, или equipment с confidence < 0.8, или qty_scope='unknown'
- **canonical_key**: транслитерированный slug для агрегации ("kirpich_polnotelyy_kr-r-po...")

### Результат Этапа 2

**Таблица `material_facts`** (основной результат):

| Поле | Пример |
|------|--------|
| raw_name | "Кирпич полнотелый КР-р-по 250x120x65/1НФ/150/2,0/50" |
| canonical_name | "Кирпич полнотелый КР-р-по 250x120x65/1НФ/150/2,0/50" |
| canonical_key | "kirpich_polnotelyy_kr-r-po_250x120x65_1nf_150_2_0_50" |
| quantity | 7.13 |
| unit | "м3" |
| gost | "ГОСТ 530-2012" |
| construction | null (или "ОГ-13" для сборок) |
| source_section | "vedomost_materialov" / "spetsifikatsiya" / "pirog" / "assembly_total" |
| block_type_display | "Таблица" / "Текст" / "Изображение" / "Расчёт" |
| kind | "material" / "equipment" |
| qty_scope | "per_unit" / "total" |
| needs_review | false |
| confidence | 0.95 |
| block_id | → doc_blocks.id → страница/блок документа |

**Таблица `product_facts`**: изделия/сборки (ОГ-13: 5 шт, ОГ-14: 13 шт...)

**View `bom_summary`**: агрегация material_facts по canonical_key — сводная ведомость материалов.

**UI**: DocumentPage → вкладки "Материалы", "Изделия", "Ведомость" для просмотра и редактирования.

## ЭТАП 3: Составление сметы (НОВОЕ — MVP)

### Входные данные

- `material_facts` из Этапа 2 (извлечённые материалы с количествами, ГОСТами, привязкой к блокам)
- `product_facts` (изделия и их количества)
- `doc_glossary` (словарь сокращений)
- Метаданные: section.code (АР, КЖ...), doc_code
- **Справочники ФСНБ-2022** (импортированные из XML ГрандСмета, см. ниже)

### Справочники ФСНБ-2022

Импорт из XML-выгрузок ГрандСмета/Smeta.ru. Хранятся в Supabase с pgvector-embedding для семантического поиска.

| Справочник | Таблица БД | Содержимое |
|------------|-----------|-----------|
| **КСР** (Классификатор строительных ресурсов) | `fsnb_resources` | Код, наименование, ед.изм., тип (материал/машина/труд), ГОСТ, цена. Embedding для RAG. |
| **ГЭСН** (Государственные элементные сметные нормы) | `fsnb_norms` | Код нормы, наименование, ед.изм., категория работ. Embedding для RAG. |
| **Состав ресурсов ГЭСН** | `fsnb_norm_resources` | Какие ресурсы (материалы, машины, труд) входят в каждую норму и в каком количестве (норма расхода). |
| **ФЕР** (Федеральные единичные расценки) | `fsnb_rates` | Код расценки, привязка к ГЭСН, стоимости (прямые, труд, материалы, машины). Embedding для RAG. |
| **Индексы пересчёта** | `fsnb_price_indices` | Региональные индексы по кварталам для пересчёта из базисных цен в текущие. |

**Поиск по справочникам (RAG)**:
1. Текст запроса → embedding (OpenRouter API, text-embedding-3-small)
2. pgvector cosine similarity → top-20 кандидатов
3. Full-text search (tsvector, русский язык) → top-10 дополнительных
4. Merge + deduplicate → финальный список кандидатов

### Архитектура: ReAct-агенты с tool_use

Каждый агент — это LLM с набором **tools (скиллов)**: функций поиска по справочникам, запросов к БД, вычислений. LLM **сам решает**, какие tools вызывать и в каком порядке (ReAct-паттерн через OpenRouter tool_use API).

```
AgentRunner (общий движок)
  │
  │  Цикл:
  │  1. Отправить system_prompt + user_message + tools[] → LLM
  │  2. LLM отвечает: tool_use (вызвать функцию) или end_turn (финальный ответ)
  │  3. Если tool_use → выполнить функцию → результат обратно в LLM → goto 1
  │  4. Если end_turn → вернуть финальный JSON-ответ
  │  5. Защита: max 10 шагов, timeout
  │
  └─ Все tools — TypeScript-функции, выполняются в браузере
```

### Phase A: Подготовка контекста (rule-based)

1. Загрузить material_facts для документа из БД
2. Сгруппировать по `construction` + `source_section`:
   ```
   Группа 1: construction="ОГ-13", materials=[Стальная труба, Полоса, Хим.анкер]
   Группа 2: construction=null, section="vedomost_materialov", materials=[Кирпич, ЦПР]
   Группа 3: construction="Сечение Л7-Л7", section="pirog", materials=[Гранит, Стяжка, Гидроизоляция]
   ```
3. Создать запись `estimates` (status='classifying')

### Phase B: Agent 1 — WorkClassifier (Классификатор работ)

**Цель**: определить, какие строительные работы нужно выполнить, исходя из материалов и контекста.

**Системный промпт**: "Ты — эксперт-сметчик. Анализируешь группы материалов из рабочей документации и определяешь виды строительных работ. Используй tools для поиска по ГЭСН."

**Tools (скиллы) агента**:

| Tool | Что делает | Зачем агенту |
|------|-----------|-------------|
| `search_norms(query, category?)` | Семантический поиск по ГЭСН | Найти, какие нормы соответствуют набору материалов |
| `search_resources(query)` | Поиск по КСР | Уточнить тип материала |
| `get_material_facts(construction)` | Загрузить материалы по конструкции | Детально изучить состав группы |
| `get_section_info()` | Код и название раздела документа | Понять контекст (АР = архитектура, КЖ = железобетон) |

**Пример работы** (автономный ReAct-цикл):

```
Агент получает: {section_code: "АР", groups: [{construction: "ОГ-13", materials: ["Полоса стальная С245", "Хим.анкер"]}]}

Шаг 1: Агент думает: "Группа ОГ-13 содержит стальные элементы и анкеры — похоже на монтаж ограждений"
        → Вызывает: search_norms("монтаж стальных ограждений лестниц", category="metalwork")
        → Получает: [{norm_code: "ГЭСН 09-03-002-01", name: "Монтаж ограждений стальных", unit: "т"}]

Шаг 2: Агент думает: "Нашёл подходящую норму ГЭСН 09-03-002-01. Записываю."
        → Финальный ответ: {work_items: [{description: "Монтаж ограждений стальных", category: "metalwork", construction: "ОГ-13", confidence: 0.88}]}
```

**Выход**: INSERT в `estimate_work_items`.

### Phase C: Agent 2 — ResourceMatcher (Сопоставитель ресурсов)

**Цель**: для каждого material_fact найти соответствующий ресурс в КСР ФСНБ-2022.

**Системный промпт**: "Ты — сметчик. Сопоставляешь материалы из проектной документации с позициями КСР ФСНБ-2022. Начинай с ГОСТ, если указан. Для каждого материала зафиксируй сопоставление через confirm_match."

**Tools (скиллы) агента**:

| Tool | Что делает | Зачем агенту |
|------|-----------|-------------|
| `search_resources(query)` | Семантический поиск по КСР | Найти ресурс по названию |
| `search_by_gost(gostCode)` | Точный поиск по ГОСТ | Быстро найти ресурс, если ГОСТ известен |
| `get_resource_details(id)` | Полная информация о ресурсе | Проверить характеристики перед подтверждением |
| `confirm_match(factId, resourceId, confidence, reasoning)` | Зафиксировать сопоставление | Сохранить результат |

**Пример работы**:

```
Агент получает: [{id: "abc", raw_name: "Кирпич полнотелый КР-р-по 250x120x65", gost: "ГОСТ 530-2012", qty: 7.13, unit: "м3"}, ...]

Шаг 1: Агент видит ГОСТ → search_by_gost("ГОСТ 530-2012")
        → Получает: [{code: "101-0782", name: "Кирпич керамический обыкновенный", unit: "тыс.шт"}]

Шаг 2: get_resource_details("101-0782") → проверяет: "Да, подходит"

Шаг 3: confirm_match(factId="abc", resourceId="101-0782", confidence=0.92,
        reasoning="ГОСТ совпадает, характеристики соответствуют")

Шаг 4: Переходит к следующему материалу...
```

**Выход**: INSERT в `estimate_resource_matches`. При confidence < 0.6 → `needs_review=true` (пользователь подтверждает через UI).

### Phase D: Agent 3 — PricePicker (Подборщик расценок)

**Цель**: для каждого вида работы подобрать расценку ГЭСН/ФЕР, проверяя, что состав ресурсов расценки покрывает фактические материалы.

**Системный промпт**: "Ты — инженер-сметчик, подбираешь расценки ГЭСН/ФЕР. Важно: состав ресурсов расценки должен покрывать фактические материалы. Используй get_norm_composition для проверки."

**Tools (скиллы) агента**:

| Tool | Что делает | Зачем агенту |
|------|-----------|-------------|
| `search_norms(query, category?)` | Поиск по ГЭСН | Найти расценки по виду работы |
| `search_rates(query, category?)` | Поиск по ФЕР | Найти единичные расценки |
| `get_norm_composition(normId)` | Загрузить состав ресурсов нормы | Проверить, какие материалы входят |
| `compare_resources(normResources, actualMaterials)` | Сравнить ресурсы | Рассчитать % покрытия |
| `confirm_rate(workItemId, rateId, confidence, coverage, reasoning)` | Зафиксировать расценку | Сохранить |

**Пример работы**:

```
Агент получает: {work_item: {description: "Устройство стяжки цементной", category: "finishing"},
                 actual_materials: [{name: "ЦПР стяжка М150", resource_code: "402-0083"}]}

Шаг 1: search_norms("устройство стяжки цементной", "finishing")
        → [{norm_code: "ГЭСН 11-01-011-01", name: "Устройство стяжек цементных"}, ...]

Шаг 2: get_norm_composition("ГЭСН 11-01-011-01")
        → [{"Раствор цементный М150", qty: 0.022, unit: "м3"}, {"Сетка арматурная", qty: 0.5}]

Шаг 3: compare_resources(norm_resources, actual_materials)
        → {coverage: 0.85, matched: ["Раствор цементный"], unmatched: ["Сетка арматурная"]}

Шаг 4: confirm_rate(workItemId, "ГЭСН 11-01-011-01", confidence=0.82, coverage=0.85,
        reasoning="Расценка покрывает основной материал, сетка не указана в спецификации но входит в норму")
```

**Выход**: INSERT в `estimate_rate_matches`.

### Phase E (MVP-упрощённо): Формирование позиций сметы

Rule-based (без агента в MVP):
1. Для каждого rate_match создать `estimate_line`
2. volume = sum(material_facts.quantity) для связанных материалов
3. source_block_ids = из material_facts.block_id (для трассируемости)
